Ante 通过**目录 (catalog)**来解析每一个提供商和模型：本文档所列即为内置的预设配置，在启动时将结合您位于 [`~/.ante/catalog.json`](#catalogjson-schema) 的自定义配置共同生效。目录配置在每个进程生命周期内只被读取一次 — 若有修改请重启 Ante 生效。

本页为详尽参考指南。有关日常如何选择提供商及直接复制粘贴的配置示例，请参阅[提供商](/usage/providers)。

## 各提供商的模型 {#models-by-provider}

每个提供商附带了一组 `preferred_models`（首选模型） — 这些就是模型选择器中显示的 ID。当您指定了某提供商但未命名模型时，Ante 默认使用其**量级最重 (heaviest-weight)** 的模型（参阅[量级分类](#weight-classes)），而不是简单地选取列表里的第一个模型。显式选择提供商具有绝对权威性：如果您传入了 `--provider`，Ante 会将您给出的模型 ID 发送至该提供商，即便该 ID 并未在其 `preferred_models` 中列出（参阅[解析过程](#how-a-model-and-provider-are-chosen)）。

#### OpenAI 传输协议 {#openai-transports}

`openai` 及 `openai-subscription` 提供商支持以两种方式流式传输响应：

| 传输协议 | 端点 | 默认 |
|---|---|---|
| `http_sse` (HTTP + SSE) | `https://api.openai.com/v1/responses` (或对应的订阅端点) | ✅ |
| `websocket_auto` (持久化 WebSocket) | `wss://.../v1/responses` | 可选 |

WebSocket 模式会为每一次会话保持单一连接始终打开，并利用 `previous_response_id` 附加新的输入项来继续对话。在较长的智能体工具循环中，这消除了每一轮往返延迟。详细底层协议信息，请参阅 OpenAI 的 [WebSocket 模式指南](https://developers.openai.com/api/docs/guides/websocket-mode)。

通过配置进程范围的环境变量进行选用（默认为 `http_sse`）：

```bash
ANTE_OPENAI_TRANSPORT=websocket_auto ante --provider openai --model gpt-5-mini
```

支持的值包括：`http_sse`, `websocket_auto`。未知的参数将触发警告并回退至 `http_sse`。

注意事项：

- WS 模式只在流式传输轮次（如 TUI 会话）中生效。在基于设计的无头 `--prompt` 模式下将使用非流式 `chat()` 并自动绕过 WS。
- 任何瞬间发生的 WS 故障（连接超时、网络波动）在当轮都会自动降级至 HTTP/SSE — 借此用户永远不会遇到因传输层选择造成的硬性报错。若遇到认证失败 (`401`/`403`)，系统会将当前会话之后的流程直接回退为 HTTP/SSE。
- 该功能在访问 `api.openai.com` (API-key) 以及位于 `chatgpt.com/backend-api/codex` 的 ChatGPT 订阅后端的应用上皆可正常运作。
- 如何验证启用的协议模式：在 debug 编译版中，开启 debug 浮窗（`Ctrl+L`）并在 **Info** 选项卡下查看 `OpenAI Transport:` 一行；或者可以直接用 grep 筛选您的会话日志来寻找 `transport selected` 的记录：

  ```bash
  grep "transport selected" ~/.ante/logs/ante.*.log.*
  ```

## `catalog.json` 模式 {#catalogjson-schema}

每次启动时，`~/.ante/catalog.json` 均会叠加合并至内置默认列表之上。它提供了两个可选且基于键值对应的顶级结构对象：

```json
{
  "providers": { /* 增加或重写提供商 */ },
  "models":    { /* 覆盖对应现有模型字段值 */ }
}
```

如果 `providers` 中有任何一个键匹配到相应的内置提供商（譬如 `openai`），系统便会依循字段对它进行局部覆写操作（patch）；倘若是属于全新品名的一项新键条，系统则将其作新增处理。这里的映射键（map key）代表正是通过 `--provider` 传递的内容 id，这确保了各条设置中的 `id` 一直匹配它对应的键标识。

:::note
通过配置环境变量 `ANTE_HOME`，您可以重定位原为 `~/.ante` 的工作路径；同理目录文件亦永远指向 `$ANTE_HOME/catalog.json`。
:::

### 提供商相关字段 {#provider-fields}

| 字段 | 必填项 | 描述 |
|---|---|---|
| `id` | ✅ | 提供商的唯一 ID，它不仅要求务必和对应外层的映射键一致 (`name` 常规被默认为旧版继承名称对待)，此字段也是您赋予 `--provider` 指令的有效参数。 |
| `display_name` | 对新增提供商：选填 | 用以展示于终端 TUI 表界面的好记名字。对省略填入的新增提供商，其默认名称等同于 ID 值。 |
| `base_url` | 对新增提供商：✅ | API 提供商的主请求前置地址。 |
| `wire_style` | 对新增提供商：✅ | Ante 所采用通讯数据封装规格 — 如 `AnthropicMessage`、`OpenAiCompatible`、`OpenAiResponse` 或 `Gemini`。 |
| `auth` | — | 定义何种核验机制来校验合法性 (详请参看 [认证方式](#authentication))。忽略时系统视之为免鉴权的无密钥对接情况。 |
| `http_headers` | — | 针对每项发往目标的 HTTP 网络请求所自动注入的拓展标头集合；该内容形式应以标准的字符串映射键值形式呈现。 |
| `supports_web_search` | — | 此项设置用于指明该系统原生平台是否具备开箱可用的互联网访问检索能力；选配为 `true` 的情况下将允许开启智能体的对应搜寻配置；此字段默认选向为 `false`，届时也就关闭且未供给关联性 `WebSearch` 扩展工具调用。 |
| `preferred_models` | — | 模型列表。它们将被应用以生成此提供商内对应的下拉候选项，同时被用作默认的基础设定资源（具体见[模型字段选项](#model-fields)）。在应用到已知系统提供商身上时，这些标识项将形成补丁；对应没出现在主单里的项则被附在下尾；完全忽略这项内容会导致系统继承保留默认的原单列表不变。 |

```json
{
  "providers": {
    "my-provider": {
      "id": "my-provider",
      "display_name": "My Provider",
      "base_url": "https://api.example.com/v1",
      "wire_style": "OpenAiCompatible",
      "auth": { "bearer": { "env_key": "MY_PROVIDER_API_KEY" } },
      "http_headers": { "X-Org": "my-team" },
      "preferred_models": [
        {
          "id": "my-model",
          "description": "My fine-tuned model",
          "max_tokens": 32000,
          "context_limit": 200000,
          "thinking": "Enabled"
        }
      ]
    }
  }
}
```

针对内置提供商而言，只需录入计划需要变动的部分。如果在那些可变选定配置属性赋以 `null` 值，等同于指令系统抹平对应已包含内容。如果打算改挂接到本机的无签名中转网关进行运作此种手段最奏效了：

```json
{
  "providers": {
    "openai": {
      "base_url": "http://localhost:8080/v1",
      "auth": null,
      "http_headers": null
    }
  }
}
```

### 认证方式 {#authentication}

通过一种带特定标签对象的 `auth` 机制用来定位凭证最终存放之处。该凭证形式要么隶属外部环节指定的环境变量(`env_key`)，要么属 Ante 授权许可内置的某种 OAuth 用户登入流（`oauth_preset`）。

| 形式 | JSON 代码 | 发送形式 |
|---|---|---|
| Bearer token（不记名令牌） | `{ "bearer": { "env_key": "MY_KEY" } }` | `Authorization: Bearer <token>` |
| 自定义头部 (Custom header) | `{ "header": { "name": "x-api-key", "env_key": "MY_KEY" } }` | `<name>: <token>` |
| Query 参数 | `{ "query": { "name": "api_key", "env_key": "MY_KEY" } }` | `?<name>=<token>` |

如果将原本对应到环境变量设置处的 `env_key` 替变为系统认定的特定内置式 OAuth 连接标签（例如 `anthropic`、`openai` 或是 `antix`）配置名称，则会触发授权机制登录，取代从系统环境参数拿取信息的方式：

```json
"auth": { "bearer": { "oauth_preset": "anthropic" } }
```

提供商一旦存有此验证相关资料配置项（无论是存在有效环境变量不为空集，或盘里正妥善拥有记录着 OAuth Token）均被归为经由认真筛选并验证成功的一列。全未定义过鉴权信息的服务亦常会全作自动放行认定处理；倘由于信息不足导致登录鉴定未完成的服务系统将其在探测自鉴阶段进行顺延规避并在选择项的排列中移送后备排布。

### 模型字段 {#model-fields}

下列描述模型的字段不仅能够在特定的 `preferred_models` 领域（这种状态中 `id` 项目必受定义要求），同样在非局限全局级别的 `models` 板块里（这时候只需提供对应用映射名字作为默认身份标记即可生效）作调整处理；其中仅仅保留该唯一的必需项识别标志 id 之后，全部相关字段全都呈现为可留空配置的状态：

| 字段 | 描述 |
|---|---|
| `id` | 模型独一无二的编号（ID）标识项。在隶属于 `preferred_models` 的定义内容中属于关键硬性内容要求项，也作映射名字时所替代补全的对象(`name`可作其向下版本名称兼顾用语看待)；在作为局部归类配置环境里的映射标签项目时会被当作有效键获取。 |
| `display_name` | 对外友好型的便于识读的展示名称。 |
| `description` | 处于模型选中菜单清单界面中的精短性简述文案。 |
| `temperature` | 执行概率抽样采样的环境“温度”值设定。 |
| `top_p` | 模型采用阈值切分的动态截断采样的阀门上限（Nucleus sampling cutoff）。 |
| `top_k` | 固定项数数量上限的动态顶限截断概率控制指标（Top-k sampling cutoff）。 |
| `max_tokens` | 控制执行产出的最终单一问询循环产出文本的最大代币长度限定阈值（Maximum output tokens）。 |
| `stop_sequences` | 定义用以控制提前休止发出的终端强制结束生成的符集信息清单。 |
| `context_limit` | 上下文边界大小容量；换言说是用该模型的处理能力 Token 限定衡量标准。 |
| `thinking` | 定义处理对应思辨力逻辑消耗深度规格档位参数内容 — 设定值容纳：`Disabled`、`Enabled`、`Deep`、以及 `Max`。 |
| `weight_class` | 系统内置用于区分不同开支重量配置与运作层级定位（`Feather`、`Middle` 以及 `Heavy`）；借由它作为自动化判断调度默认选择方案或辅属调派指令的标准(有关指点细节参考 [量级分类](#weight-classes))。 |
| `support_vision` | 用以决定当前对应这套生成模块结构能否被当做应对画面分析处理视觉解析作业用；如果在缺乏明言指示定义时被调回依据该模型自身的 ID 被用作系统内测指标判定。需要说明的一个相关重要事宜为倘若是对非相关图文识别能力体系进行图像资料提交解读指令后产出的将只是图像表册内的一些描述型元数据，而非真正的内部结构元素辨识。 |

这个隶属上层位置分布配置项领域的 `models` 可随时基于已知目标对应编号发挥灵活补充修订并整合的最终覆盖功效，甚至能在合并到基础运行系统里的最后环节进行终层判定替换；所有未被干预的内容体系一如既往沿用空本默认底册配置。

```json
{
  "models": {
    "claude-sonnet-4-6": { "thinking": "Deep", "max_tokens": 64000 }
  }
}
```

### 量级分类 {#weight-classes}

每一套已记录在案的模型配置都搭配拥有一项专门标定它属于哪个系统级次区分规格 `weight_class` 设定：`Feather`（体现小量、速度迅捷、成本相对经济特点）、`Middle`（居间性折中），又或是 `Heavy`（包含有极致复杂度和能力全面强大的庞大体格）；基于此类配置特征选项决定了用户没有明确指定的任务下进行智能自主选型时依赖的选择条件规则。

- **默认首发选定项 (Default model)** — 单一设定提供商但不专门划配详细模型选项参数内容下，自动解析选择分配同类型系列清单里具备极具对应庞然体量 `Heavy`（重量级最重规模配置参数标准） 的项目投入部署使用。
- **关联性质协同辅助调用安排 (Auxiliary calls)** — 面对无需复杂繁重解析耗用且只关乎轻微执行成本的小开销型内接作业（像是 `WebFetch` 负责整理生成的文案收罗统括简报总结等工序需求）调用执行，选用对应的该供给端下辖分类当中极小号 `Feather` 轻型模型规格去应接负责落实处理。

当处于没有获得任何特殊设定分配指定项的被识别名册之列中这批没赋有相应配置参数标签的对象都会遵循原有基础库结构目录配置项排列的固定先后次序作相应顺位接替执行选用安排；一旦对于属于私建扩充列表里的这些个体模型添加录写了这个专项 `weight_class` 标签内容之后也将按上述规例准则去接引运作流程导向规划。

## 提供商与模型是如何被选取的 {#how-a-model-and-provider-are-chosen}

当 Ante 解析一个模型 ID 时，它会层叠三个来源，以最后的来源优先为准：

1. **底层官方参考规格 (Canonical spec)** — 依照配置目录排列次序排定最前边位置且能在它附设对应的 `preferred_models` 项下登记着被指定名字对象的该项目归类，如果碰到了尚未归属于其辖列中已知范围的配置项目名册将无缝自动调入到裸模型（bare default spec）环境作为备底处理。
2. **通过配置选项产生的强制内容调改 (models override)** — 根据其所属系统名在局部或非特许框架限定结构里面发起的有关它该 ID 各类修订及更动覆盖内容配置修补参数。
3. **基于当前直接指令或者相关环境变量产生的高优先级参数覆盖 (Environment overrides)** — 列在这里作为流程进程级别的这系列高优先级指派控制操作将享有绝对越过所有的预设条件设置产生强制性的约束。

这些选定的不同类别服务支持供给商也被绑定到了上述相应名称类型模块范畴当中；假如仅通过 `--model` 下发一个指向具体的被要求执行调用目标名称指令时那系统便依据条件自查匹配属于哪些经过验证确凿在册合法身份注册登记的各个对应的 `preferred_models` 范围名录项里面提取出首获对位关联相连的供应商作为主对接资源调用；如果没有在相关合法对象列表项下查找到也会退一步在虽未经显要列表展示但是被系统认为符合合法权限范围登记列表里头执行首个备配对象调用；一旦均不存在前两者条件状态即降配至系统默设最低基础供应商服务状态资源去提供支援。

在执行 `--provider` 和 `--model` 同期设定调出的这两种双规制设定前提保障情况下，前置条件限定必须要满足对应获得所指名确定的相关供给服务商身份拥有认证背书资格方会发挥决定权统驭优先级分配。系统内部的逻辑流程一如既往以对全局域性指定名确的对象ID参数启动搜检为发端进行作业：处于获悉确定名单名列之中的目标即便身处于转拨它系它属其他机构环境里运营仍然沿袭享有属于本身对应类别体系参数内容与使用者强制自定义重载规则配置；相对那批未知状态不明出处的体系配置名字将一概采取去配置外带包装修饰的直传数据接管策略方式作为普通基础服务对接运转工作。

假如没有获得这两种指令 `--model`/`--provider` 的赋令支持系统就触发智能化自运行探寻与检测的模式运作响应了: 它启动并激活系统资源配置库记录在排前顺次具备确凿身份证明授权服务准入机构内被标定了具备当前可调遣最丰裕宏大级别的模型结构（可以一窥前文了解所谓的[量级分类](#weight-classes)设定情况说明）用来满足响应需求任务的部署处理环节执行动作；假定所有项目没有一项符合通过许可验证规则认证流程判定都将被安排引流到通用的保底备项 `local` 去兜底担纲最后执行处理环节。

## 环境变量覆盖机制 {#environment-overrides}

这组进程级别的相关设置参数在实际运行的过程中起到对同一时段相关系统所运行的会话设定起直接发挥更改指令与调改统御优先决定主导作用，而并不要再依靠通过重写文本修改的方式达到调拨成效了：

| 变量名称 | 改写的对象目标 |
|---|---|
| `MODEL_BASE_URL` | 所有服务提供商对接统一目标调用的主路径连接网址设置参数 (如果一旦系统查出有如同 `ANTHROPIC_BASE_URL` 专门对应各自不同厂商提供的个性专属通道设定选项这方更受拥护占优先支配级设定) 。 |
| `MODEL_TEMPERATURE` | 用以影响随机变化生成属性结果概率表现设定的对应值 `temperature`。 |
| `MODEL_TOP_P` | 同对应着截段数值属性设置相关联配置 `top_p`。 |
| `MODEL_MAX_TOKENS` | 同理对应覆盖代换输出总代币数最高容量数控制额定阈值项的对应参数内容 `max_tokens`。 |
| `MODEL_CONTEXT_LIMIT` | 对应调改管控可接纳最大阅读容忍上下文总信息文本载量相关的设定值项 `context_limit`。 |
| `MODEL_THINKING` | 用于调控深度逻辑处理运算级别负重度设置对应关联的参数数值设置 `thinking` — 可接纳的受配置指令项包含： `none`、`enabled`、`deep` 或 `max`。 |

很多内置的预设还会优先选用有针对性的定制基础地址（base URL）环境配置参数项从而覆盖取代针对普通共性设置制定的综合通用调换指令配置选项 `MODEL_BASE_URL`，它们这些拥有更高支配设定指令的专用特指通道包含如下项目名称配置：`ANTHROPIC_BASE_URL`、`OPENAI_BASE_URL`、`OPENAI_COMPATIBLE_BASE_URL` 以及 `DEEPSEEK_BASE_URL`。

## 错误处理 {#error-handling}

当配置文档里其中一单条目不符合规定出现瑕疵不规范情形错误也不致影响使整篇文本产生完全奔溃宕机不可恢复运转故障的局面；针对此份名录档案结构文档即 `catalog.json` 在系统读取接管校验阶段采取的是宽松兼容的容错弹性执行审查策略进行对待处理运作方式方法应对解决：假如期间发觉存在任何没法通过正常验证反序列化校验流程解析查出异常项或不合法内容定义归属于相关供应商及相应模型配置条块名目皆作跳行略弃剔出不做解析理睬应对手段从而不致干涉后边排序列正文照例载读装载顺序列进程发挥其生效；遇到这种情况产生此类报错信息也会同步即刻展现告知对应问题排错原因显示于在启动前线位置的加载播报状态信息界面上显示供审阅，示例参考如下所示意结果：

```
Skipped 1 entry in ~/.ante/catalog.json:
  - providers.my-provider: missing field `base_url`
```

只要确保配置文档不是连基本合规的合法 JSON 语法对象规范形式全完全乱了套的情况否则一概会被强制执行直接彻底否决；如果该份名录配置文本自身并没有任何保存存在即便真的在盘内系统寻找失落状态这也并非什么事态重大的棘手大不了的错误情况的出现 — 直接触发调转启用系统原配随装即有随地可供差遣使用的内部默认名录体系即行。
