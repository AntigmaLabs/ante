## Overview

Ante follows a clean separation of concerns with a client-daemon architecture. The UI and core logic are decoupled through message passing, making it possible to swap frontends (TUI, headless) without changing the underlying engine.

## Client-Daemon split

```
┌────────────────┐          ┌─────────────────────────────┐
│     Client      │    Op    │          Daemon              │
│                 │ ───────▶ │                              │
│  TUI / Headless │          │  Session ─▶ Turn ─▶ Step    │
│  or Serve       │ ◀─────── │                              │
│                 │    Evt   │  Tools    Providers   Store  │
└────────────────┘          └─────────────────────────────┘
```

- **Client** — The user-facing layer. The ratatui-based TUI, headless CLI runner, or an external process connected via `ante serve`. Sends `Op` operations and renders `Evt` events.
- **Daemon** — The core engine. Receives operations, manages sessions, dispatches to LLM providers, schedules tool execution, and emits events.
- **Transport** — Tokio channels for in-process clients (TUI, headless). External clients use JSONL over stdio, a Unix socket, or WebSocket through `ante serve`. See [Transport](/reference/protocol-reference#transport) for details.

The [Protocol Reference](/reference/protocol-reference) defines every operation and event.

## LLM providers

Ante is provider-agnostic. At session startup it resolves the provider, model, and credential from CLI options or saved preferences. The provider adapter translates the conversation and tool calls into the provider's API format and converts responses back into session events.

Transient mid-stream failures reconnect within the turn. A stalled call times out after a per-provider idle window, set with [`stream_idle_timeout_secs`](/reference/catalog-reference#provider-fields). See [Connect a provider](/usage/providers) for sign-in and keys.

## Tool system

The daemon runs tool calls the model requests, after checking them against [permission rules](/configuration/permission). Built-in tools cover file I/O, shell, web access, sub-agents, and structured questions; [MCP servers](/extend/mcp) add more. The [Tools Reference](/reference/tools-reference) lists each tool, the default set, and filtering flags.

## Session lifecycle

1. Client sends `Op::StartSession` with model, provider, and policy
2. Daemon resolves the provider, authenticates, discovers skills and sub-agents
3. Daemon creates a `Session` and emits `Evt::SessionStart`
4. User sends `Op::UserInput` to start a turn
5. Session spawns a `Turn` which communicates with the LLM
6. Turn executes tools, requests approvals, and eventually completes
7. As the conversation approaches the context limit, Ante [compacts](/reference/protocol-reference#concepts) older history
