Ante keeps project memory across conversations so you can carry useful feedback, preferences, and decisions into later work without repeating them.

## How it works

Each project has a memory directory at `~/.ante/projects/<project-id>/memory/`, where `<project-id>` is a sanitized form of the project's absolute path. `MEMORY.md` is the index: Ante reads it when a session starts or resumes and includes it in the context before the conversation. The system prompt holds the general memory instructions; the project directory and index travel in a separate reminder prepared at each turn's start.

Auto-memory is enabled by default in the interactive TUI and disabled by default in headless `-p` runs. Use `--enable-auto-memory` to opt a headless run into memory, or `--disable-auto-memory` to turn it off for a TUI session. To make either choice persistent, set `auto_memory` in [`settings.json`](/configuration/preference#settings-file).

A replacement system prompt disables built-in auto-memory for a fresh session. A resumed session includes the current index only when auto-memory is enabled and its saved system prompts contain Ante's memory instructions. Saved prompts themselves are preserved.

### Automatic behavior

As the agent works on your project, it:

1. **Consults** existing memory files to build on previous experience
2. **Records** new insights when it encounters common mistakes or useful patterns
3. **Updates** or removes memories that turn out to be wrong or outdated

### MEMORY.md

The main memory index is included up to a cap of 200 lines or 25 KB, whichever comes first (a truncation note is appended when it overflows). Keep one short pointer per memory and put details in topic files:

```markdown title="MEMORY.md"
# Project memory

- [Review feedback](review-feedback.md) — how the team prefers changes grouped
- [Release context](release-context.md) — why the rollout is staged
- [Service ownership](service-ownership.md) — where to check the current owner
```

### Topic files

For detailed notes, create separate files and reference them from `MEMORY.md`:

```
memory/
├── MEMORY.md             # Index (auto-loaded, max 200 lines or 25 KB)
├── review-feedback.md    # Confirmed working preferences
├── release-context.md    # Decision context not recorded in the repo
└── service-ownership.md  # Pointer to an external source of truth
```

## Memory types

When auto-memory is on, the agent is taught to save **typed** memories — each topic file carries `name`, `description`, and `type` frontmatter so future sessions can decide what is relevant. There are four types:

| Type | What it captures |
|---|---|
| `user` | The user's role, expertise, goals, and preferences — so explanations and defaults can be tailored to them. |
| `feedback` | Guidance on how to work in this project, drawn from corrections and confirmations alike. Leads with the rule, then a **Why** and **How to apply** line. |
| `project` | Ongoing work, decisions, or constraints not derivable from code or git. Same **Why** / **How to apply** structure; relative dates are stored as absolute. |
| `reference` | Pointers to where current truth lives in external systems (a Linear project, a Grafana board, a Slack channel). |

A typed topic file looks like:

```markdown
---
name: bundle-refactors
description: Prefer one bundled PR for refactors in this area
type: feedback
---

For multi-file refactors here, prefer a single bundled PR over splitting.

**Why:** the user confirmed it — a validated call, not a correction.
**How to apply:** multi-file refactors touching this area.
```

The agent deliberately **does not** save secrets, in-progress task state, or anything already re-readable from the repo (code structure, file paths, conventions — those belong in `AGENTS.md`). Recalled memory is treated as background context that reflects a past moment, so the agent re-verifies any file, flag, or function a memory names before acting on it.

## Guidelines

The memory system follows these principles:

- **Concise** — `MEMORY.md` is truncated after 200 lines, so keep it focused
- **Semantic** — Organize by topic, not chronologically
- **Accurate** — Update or remove outdated information
- **Actionable** — Record what worked, what didn't, and why

## Importing Claude Code memory

`/import-claude` copies Claude Code's project memory for the current directory — the top-level `.md` files under `~/.claude/projects/<project-dir>/memory/` — into Ante's project memory. Existing Ante files are never overwritten, so re-running the command is a clean no-op. The command reports which files were imported and which were skipped because they already existed.

## Memory is per-project

Memory is scoped to each project directory. Different projects have independent memory directories. This means the agent's accumulated knowledge about your React frontend won't interfere with its knowledge about your Rust backend.

## Manual editing

You can edit memory files directly — they are plain markdown. The agent can also update them using the `Write` and `Edit` tools during a session. The index is read from disk at session start or resume, not on every turn. To use an external edit in an already open conversation, ask the agent to read the changed file or resume the session to reload the index.
